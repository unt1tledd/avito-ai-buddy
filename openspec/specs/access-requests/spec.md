# access-requests Specification

## Purpose

Описать подтверждённый процесс заявок на доступ: черновик в ответе AI, явное подтверждение владельцем, асинхронное создание в Task, решение доверенного tracker и сохранение результата в Chat. Область выделена по реальному backend и интеграционным тестам; общий трекер задач и фактическая выдача прав сюда не входят.

## Requirements

### Requirement: Черновик с проверенным ресурсом и уровнем

AI SHALL формировать черновик по политике текущего процитированного источника. ID и название фиксированного ресурса берутся из политики. Для репозитория требуется нормализованный HTTPS URL из текущего или сохранённого пользовательского сообщения на разрешённом host. Неподдержанный явно выбранный уровень не заменяется автоматически. Уровень по умолчанию допустим только при единственном варианте политики и отсутствии противоречащего выбора.

#### Scenario: Конкретный допустимый ресурс
- **WHEN** выбор ресурса и уровня проходит проверку текущей процитированной политики
- **THEN** AI возвращает `resource_id`, `resource_label`, `access_level`, а Chat сохраняет предложение с собственным ID при сохранении ответа

#### Scenario: Нет допустимого выбора
- **WHEN** ресурс неоднозначен, исключён, уровень не поддержан или URL репозитория не подтверждён пользовательским сообщением
- **THEN** проверка отклоняет черновик, и допустимый proposal без исправления выбора не возвращается
- **AND** указание ресурса шага не отменяет проверку политики

### Requirement: Явное подтверждение владельцем

Сервис Chat SHALL предоставлять `POST /v1/chat/proposals/{proposal_id}/confirm`, требовать действительный access-токен владельца предложения в видимом диалоге и проверять срок первоначального подтверждения. Срок задаётся `CHAT_PROPOSAL_TTL`, по умолчанию 24 часа. Подтверждение атомарно сохраняет `pending_dispatch` и команду в outbox; оно не является синхронным созданием Task или выдачей доступа.

#### Scenario: Подтверждение действительного черновика
- **WHEN** владелец подтверждает ещё действительное предложение впервые
- **THEN** возвращается `access_request.status=pending_dispatch`, а состояние и команда сохраняются вместе
- **AND** шаг адаптации не завершается

#### Scenario: Чужое или просроченное предложение
- **WHEN** другой пользователь подтверждает предложение либо оно недоступно после удаления диалога
- **THEN** возвращается `NotFound` без отправки команды
- **AND** первоначальное подтверждение после TTL возвращает `FailedPrecondition`, отсутствие/недействительность сессии — `Unauthenticated`

### Requirement: Повтор подтверждения и доставка команды

Сервисы Chat и Task SHALL обеспечивать одну заявку на `proposal_id` при повторах подтверждения и доставки. Chat публикует команду из сохранённого outbox в Kafka; Task проверяет положительные ID и непустые ресурс/уровень, получает команду пользователя через User и сохраняет заявку со статусом `pending`. Повторный payload с тем же предложением, но другим пользователем, ресурсом или уровнем отклоняется как конфликт.

#### Scenario: Повторная доставка
- **WHEN** одно предложение подтверждено несколько раз или его команда повторно доставлена
- **THEN** Task содержит одну заявку с теми же владельцем, ресурсом и уровнем

#### Scenario: Зависимость недоступна
- **WHEN** публикация команды или получение метаданных пользователя завершается ошибкой
- **THEN** backend не сообщает о создании Task без успешного сохранения
- **AND** обработка использует предусмотренные очередью повторы и обработку отказов; срок доставки пользователю не гарантируется этой спецификацией

### Requirement: Подтверждение создания и ошибка обработки Task

Task SHALL публиковать результат обработки команды до commit её Kafka offset. Сохранённая заявка подтверждается событием `pending` с ID Task; окончательный сбой без созданной заявки — `failed` после подтверждения записи в DLQ. Chat обновляет предложение по результату Task. Успешная публикация команды из Chat сама по себе не переводит карточку из `pending_dispatch` в `pending`.

#### Scenario: Заявка действительно создана
- **WHEN** Task сохранил заявку и событие создания доставлено в Chat
- **THEN** карточка получает `pending` и ID сохранённой заявки
- **AND** повтор команды возвращает существующую заявку и не создаёт дубликат

#### Scenario: Создание завершилось ошибкой
- **WHEN** обработка идентифицируемой команды исчерпана, запись в DLQ подтверждена и по предложению нет заявки
- **THEN** Task публикует `failed` для этой попытки до commit offset, а Chat сохраняет ошибку для чтения истории и повторной отправки
- **AND** при недоступном подтверждении результата offset не фиксируется

#### Scenario: Результат создания неизвестен
- **WHEN** обработчик получил ошибку, но повторное чтение обнаруживает уже созданную заявку того же пользователя
- **THEN** публикуется её фактический статус вместо ложного `failed`
- **AND** ошибка чтения БД повторяется до выяснения результата; неидентифицируемая команда остаётся в DLQ без изменения чужого пользовательского состояния

### Requirement: Повтор после сбоя доставки

Chat SHALL сохранять терминальный `FAILED` outbox после исчерпания автоматических попыток и позволять владельцу повторить ту же заявку до TTL при локальном сбое либо `failed` от Task. Повтор сбрасывает outbox и записывает новый `dispatch_id` в команду той же записи. Промежуточные события проверяются по текущей попытке; решения approved/rejected не откатываются промежуточными статусами.

#### Scenario: Повтор терминально неуспешной отправки
- **WHEN** outbox находится в `FAILED`, а владелец повторно подтверждает неистёкшее предложение
- **THEN** история показывает `failed`, карточка предлагает повтор, а подтверждение возвращает ту же запись outbox в очередь со сброшенным счётчиком и новым `dispatch_id`
- **AND** запрос подтверждения получает `pending_dispatch`

#### Scenario: Повтор после DLQ Task
- **WHEN** Chat получил `failed` от Task, хотя локальный outbox уже имеет `SUCCESS`, и TTL ещё не истёк
- **THEN** повтор разрешён, команда обновляется с новым ID попытки и повторно отправляется
- **AND** запоздалое `failed` или `pending` старой попытки не меняет текущее предложение

#### Scenario: Истёкшее предложение после сбоя
- **WHEN** TTL уже истёк после локального сбоя отправки либо ошибки обработки Task
- **THEN** повтор не ставит команду в очередь и возвращает `FailedPrecondition`

#### Scenario: Окончательное решение сохранено
- **WHEN** после approved/rejected приходят запоздалые промежуточные события или повторяется подтверждение
- **THEN** решение сохраняется и новая команда не создаётся

### Requirement: Чтение заявок владельцем и tracker

Сервис Task SHALL предоставлять владельцу `GET /v1/tasks/{user_id}` по его пользовательскому access-токену и tracker — список ожидающих `GET /internal/v1/tasks` по tracker credentials с фильтром `team_id`. Поддержаны `after_id >= 0` и `limit` от 1 до 100; записи идут по возрастанию ID, пустая HTTP-выдача — `[]`. HTTP-поля Task используют protobuf snake_case.

#### Scenario: Собственные заявки
- **WHEN** пользователь читает собственный список с допустимым курсором
- **THEN** возвращается соответствующая страница его отправленных заявок со статусами и реквизитами
- **AND** неподтверждённые черновики Chat в список Task не включаются

#### Scenario: Разделение полномочий
- **WHEN** пользователь запрашивает чужой список
- **THEN** возвращается `PermissionDenied`
- **AND** tracker-токен для пользовательского списка, обычная сессия для tracker-списка или отсутствие нужных credentials дают `Unauthenticated`

#### Scenario: Ошибки параметров
- **WHEN** `team_id` или `user_id` неположителен, `after_id` отрицателен либо явно заданный `limit` вне диапазона
- **THEN** запрос отклоняется как `InvalidArgument`

### Requirement: Список заявок в интерфейсе

Frontend SHALL загружать собственные заявки из Task по страницам до конца списка, сохранять точность строковых int64 ID и показывать ресурс, уровень доступа, номер и статус в порядке от новых к старым. Клиент поддерживает snake_case и совместимый camelCase с приоритетом snake_case. Пустой список отличается от ошибки загрузки; интерфейс пользователя не предоставляет полномочий tracker.

#### Scenario: Реквизиты и статусы из Task
- **WHEN** Task возвращает допустимый список собственных заявок
- **THEN** карточки показывают ресурс, уровень и внешний номер либо ID Task при его отсутствии; дата создания используется для сортировки
- **AND** статусы pending, approved и rejected отображаются соответственно как ожидание решения, одобрение и отказ; черновики Chat в этот список не добавляются

#### Scenario: Несколько страниц и большие ID
- **WHEN** страница содержит 100 записей, включая ID `9007199254740993`
- **THEN** следующая страница запрашивается с точным ID последней записи в `after_id` без преобразования в JavaScript Number
- **AND** загрузка продолжается до страницы короче 100 записей, после чего объединённый список сортируется по дате от новых к старым

#### Scenario: Пустой список
- **WHEN** успешная загрузка всех страниц не вернула заявок
- **THEN** показывается состояние отсутствия заявок, а не ошибка

#### Scenario: Ошибка загрузки или курсора
- **WHEN** запрос страницы завершился ошибкой, ответ не является массивом либо следующему курсору нельзя придать положительное продвижение
- **THEN** загрузка завершается ошибкой без бесконечного обхода страниц, интерфейс показывает ошибку и действие обновления
- **AND** ранее загруженный список при неудачном обновлении сохраняется; частичный результат нового обхода не выдаётся за успешно обновлённый список

### Requirement: Решение доверенного tracker

Сервис Task SHALL принимать `PUT /internal/v1/tasks/{task_id}/decision` только с tracker credentials, положительными ID задачи, команды и решающего лица и статусом approved или rejected. Решение применяется только к ожидающей заявке указанной команды и сохраняется вместе с событием outbox. Это доверенная запись решения внешним клиентом; проверка должности решающего лица в User этим контрактом не заявляется.

#### Scenario: Одобрение или отказ
- **WHEN** tracker передаёт допустимое решение для ожидающей заявки своей указанной команды
- **THEN** сохраняются итоговый статус, время, ID решающего лица, комментарий и внешний ID при наличии
- **AND** заявка исчезает из списка ожидающих и событие решения сохраняется в той же транзакции

#### Scenario: Идемпотентность и конкурирующие решения
- **WHEN** tracker повторяет полностью совпадающее сохранённое решение
- **THEN** возвращается прежний результат без нового решения
- **AND** отличающееся повторное решение даёт `AlreadyExists`; при конкурирующих одобрении и отказе сохраняется ровно одно

#### Scenario: Чужая команда и недопустимый статус
- **WHEN** заявка не относится к указанной команде
- **THEN** возвращается `NotFound`
- **AND** статус, отличный от approved/rejected, отклоняется как `InvalidArgument`

#### Scenario: Внешний номер уже принадлежит другой заявке
- **WHEN** tracker передаёт непустой `external_request_id`, уже сохранённый у другой заявки
- **THEN** возвращается `AlreadyExists`, исходная заявка сохраняет прежний статус и реквизиты
- **AND** событие нового решения не сохраняется, а другая заявка не изменяется

### Requirement: Сохранение результата в исходной переписке

Сервис Chat SHALL принимать события решений Task через Kafka, обновлять связанное предложение и сохранять сообщение о решении с дедупликацией. WebSocket-публикация выполняется после сохранения и остаётся best effort. Решение не означает фактическую выдачу прав и не изменяет прогресс Onboarding.

#### Scenario: Пользователь был офлайн
- **WHEN** решение Task доставлено, а исходный диалог видим
- **THEN** статус и реквизиты обновляются в предложении, сообщение о решении сохраняется один раз
- **AND** результат доступен при последующем чтении истории независимо от WebSocket

#### Scenario: Повтор события или удалённый диалог
- **WHEN** событие решения доставляется повторно
- **THEN** повторное сообщение о том же решении не создаётся
- **AND** удалённый диалог не восстанавливается ради уведомления
