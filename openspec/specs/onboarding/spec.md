# onboarding Specification

## Purpose

Предоставлять назначенный план адаптации стажёра, описания и порядок шагов, текущий шаг каждого трека и сохранённый прогресс. Backend назначения существует; инициатор назначения в пользовательском процессе остаётся вопросом согласования и не определяется этой спецификацией.

## Requirements

### Requirement: Состав и повторное назначение плана

Сервис Onboarding SHALL обрабатывать разрешённый запрос `AssignPlan` / `POST /v1/users/{user_id}/plan`, формируя один план пользователя из существующих шаблонов `common` и выбранного профессионального трека. Ключ трека нормализуется удалением пробелов и приведением к нижнему регистру. Повтор назначения того же трека не создаёт дубликаты плана и шагов и сохраняет прогресс.

#### Scenario: Назначение с существующими шаблонами
- **WHEN** разрешённый запрос задаёт трек с профессиональными шаблонами
- **THEN** возвращается план с общими и профессиональными шагами

#### Scenario: Повторное назначение
- **WHEN** тому же пользователю повторно назначается тот же трек
- **THEN** возвращается тот же план без дубликатов шагов и потери отметок выполнения

#### Scenario: Неизвестный или конфликтующий трек
- **WHEN** для запрошенного профессионального трека нет шаблонов
- **THEN** возвращается `InvalidArgument` без создания частичного плана
- **AND** попытка заменить трек уже существующего плана через AssignPlan возвращает `AlreadyExists`

### Requirement: Определение трека при отсутствии явного значения

Сервис Onboarding SHALL при разрешённом AssignPlan без непустого `track` возвращать существующий план, а для нового плана получать направление из метаданных User. Ошибка User не должна приводить к назначению выдуманного или произвольного трека.

#### Scenario: План уже существует
- **WHEN** `track` не задан и у пользователя есть план
- **THEN** возвращается существующий план с его шагами

#### Scenario: Новый план по метаданным
- **WHEN** `track` не задан, плана нет, а User вернул поддерживаемое направление
- **THEN** назначается план этого нормализованного направления

#### Scenario: Недостаточно метаданных
- **WHEN** User не возвращает стажировку либо недоступен или возвращает недопустимые метаданные
- **THEN** возвращается соответствующая ошибка `NotFound` или `Unavailable`, а план не назначается

### Requirement: Чтение плана и контекста треков

Сервис Onboarding SHALL предоставлять `GET /v1/users/{user_id}/plan` с назначенными шагами в порядке позиции шаблона, затем ID шаблона, и `GET /v1/users/{user_id}/plan_context` с первым незавершённым шагом каждого представленного трека. Статус шага имеет значения `pending` или `completed`; отсутствие текущего шага трека не означает завершение всей стажировки.

#### Scenario: Два незавершённых трека
- **WHEN** в общем и профессиональном треках есть незавершённые шаги
- **THEN** контекст возвращает собственный первый незавершённый шаг каждого трека с его ID, названием и доступными метаданными

#### Scenario: Завершённый трек
- **WHEN** все назначенные шаги одного трека завершены
- **THEN** трек остаётся в контексте без текущего шага, а текущие шаги остальных треков сохраняются

#### Scenario: План отсутствует
- **WHEN** план пользователю ещё не назначен
- **THEN** чтение плана возвращает `NotFound`, а контекст — пустой набор треков
- **AND** чтение не создаёт план

#### Scenario: Совместимый запрос единственного текущего шага
- **WHEN** вызывается `GET /v1/step/{user_id}/current`
- **THEN** возвращается первый незавершённый шаг всего плана в серверном порядке либо ответ без шага, если его нет
- **AND** этот ответ не подменяет контекст отдельных треков

### Requirement: Завершение и переоткрытие шага

Сервис Onboarding SHALL сохранять завершение назначенного пользователю шага через `PUT /v1/step/{user_id}/{step_id}/completion` и переоткрытие через PATCH того же пути с `status=pending`. Операция доступна и для шага, который не является текущим. Повторное завершение сохраняет первоначальную дату завершения.

#### Scenario: Завершение и повтор
- **WHEN** владелец завершает свой назначенный шаг и повторяет PUT
- **THEN** оба успешных ответа сообщают `completed`, а первоначальный момент завершения сохраняется

#### Scenario: Снятие выполнения
- **WHEN** владелец отправляет PATCH с `status=pending` для завершённого шага
- **THEN** отметка завершения снимается и шаг снова участвует в расчёте текущего шага

#### Scenario: Ошибка цели или статуса
- **WHEN** шаг не назначен пользователю
- **THEN** возвращается `NotFound`
- **AND** пустой ключ, неположительный ID пользователя или PATCH со статусом, отличным от `pending`, отклоняются как `InvalidArgument`

### Requirement: Владение планом и изменение шаблонов

Сервис Onboarding SHALL проверять пользовательский access-токен и совпадение владельца с целевым `user_id` для чтения плана, контекста и изменения прогресса; пользовательский запрос назначения также не может обращаться к чужому `user_id`. Изменение шаблона `PUT /v1/step/{step_key}` требует отдельного сервисного токена Onboarding, непустых названия и периода и положительной позиции.

#### Scenario: Чужой план или отсутствие сессии
- **WHEN** пользователь с действительным токеном обращается к чужому плану
- **THEN** возвращается `PermissionDenied`
- **AND** отсутствующий или недействительный токен даёт `Unauthenticated`; недоступность Auth не разрешает операцию

#### Scenario: Изменение шаблона доверенным клиентом
- **WHEN** клиент с сервисным токеном передаёт допустимые поля существующего шаблона
- **THEN** шаблон обновляется
- **AND** обычный пользовательский токен не допускается к этой операции, а неизвестный шаблон даёт `NotFound`

### Requirement: Отображение серверного состояния Roadmap

Frontend SHALL читать план и контекст без автоматического назначения, определять текущие шаги только по `plan_context` и после записи перечитывать серверное состояние. Группировка по трекам используется, когда каждый шаг содержит `track`; при отсутствии этих метаданных весь план остаётся видимым без вычисления трека по имени или ID шага.

#### Scenario: План пока не назначен
- **WHEN** чтение плана возвращает `404`
- **THEN** показывается состояние отсутствия назначения без фиктивного прогресса и без POST назначения

#### Scenario: Выполнение открытого текущего шага
- **WHEN** выбранный текущий шаг завершён и новый контекст указывает следующий шаг того же трека
- **THEN** интерфейс выбирает этот следующий шаг
- **AND** при отсутствии такого шага не переключается произвольно на другой трек

#### Scenario: Ошибка загрузки или сохранения
- **WHEN** чтение контекста либо запись шага завершается ошибкой
- **THEN** интерфейс показывает ошибку и возможность проверки серверного состояния
- **AND** ошибка не изображается отсутствием назначения или подтверждённым выполнением

### Requirement: Разделение прогресса и помощи AI

Frontend и Onboarding SHALL изменять выполнение только через операции прогресса; подготовка вопроса, ответ AI и подтверждение заявки не выполняют эти операции автоматически. Непустой `resource_id` шага передаётся как контекст действия `access_request`, но сам по себе не разрешает выдачу доступа.

#### Scenario: Вопрос о выбранном шаге
- **WHEN** пользователь выбирает «Спросить у AI-buddy»
- **THEN** открывается новый чат с подготовленным вопросом о выбранном шаге, который пользователь может отправить
- **AND** статус шага не меняется

#### Scenario: Подтверждение заявки из ответа
- **WHEN** пользователь подтверждает предложение доступа в чате
- **THEN** выполняется операция заявки, а шаг остаётся в прежнем состоянии до отдельного изменения прогресса
