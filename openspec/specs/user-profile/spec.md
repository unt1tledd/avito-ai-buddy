# user-profile Specification

## Purpose

Хранить профиль и сведения о стажировке пользователя AI Buddy, предоставлять их владельцу и доверенным сервисам и проверять согласованность команды, наставника и дат. Регистрация аккаунта и назначение плана адаптации остаются отдельными операциями.

## Requirements

### Requirement: Создание профиля стажировки

Сервис User SHALL предоставлять `Create` по gRPC и `POST /v1/user` по HTTP для создания профиля и стажировки. Обязательны положительные `user_id`, `team_id`, непустые имя, фамилия, направление и даты начала/планового окончания; отчество, наставник и фактическое окончание необязательны. Профиль, членство в команде и стажировка сохраняются атомарно.

#### Scenario: Успешное создание
- **WHEN** владелец передаёт допустимые данные и существующую команду
- **THEN** сохраняются профиль, членство в команде и стажировка, возвращается положительный `internship_id`
- **AND** сведения читаются через gRPC и HTTP

#### Scenario: Нормализация текстовых полей
- **WHEN** имя, фамилия, направление или отчество содержат пробелы по краям
- **THEN** эти пробелы удаляются перед сохранением, а пустое после нормализации отчество считается отсутствующим

#### Scenario: Ошибка создания
- **WHEN** одна из проверок или записей транзакции завершается ошибкой
- **THEN** новый частичный профиль, членство и стажировка не остаются сохранёнными
- **AND** последующее корректное создание может использовать исправленные данные

### Requirement: Согласованность дат и обязательных данных

Сервис User SHALL проверять даты в формате `YYYY-MM-DD`, существование календарной даты и отсутствие окончания раньше начала. Имя, фамилия и направление после удаления пробелов не могут быть пустыми.

#### Scenario: Недопустимая дата
- **WHEN** передана невозможная дата либо плановое или фактическое окончание раньше начала
- **THEN** возвращается `InvalidArgument`, а стажировка не создаётся

#### Scenario: Пустые обязательные значения
- **WHEN** обязательное текстовое значение пусто после нормализации либо обязательный ID неположителен
- **THEN** возвращается `InvalidArgument`

### Requirement: Команда и наставник

Сервис User SHALL принимать только существующую команду и, при указанном наставнике, требовать его членство в этой команде и отличие от самого стажёра. Указание наставника не создаёт ему аккаунт Auth или полномочия tracker.

#### Scenario: Наставник из команды
- **WHEN** указан существующий наставник из выбранной команды
- **THEN** связь с ним сохраняется и возвращается в метаданных

#### Scenario: Неизвестная команда или неподходящий наставник
- **WHEN** команда не существует
- **THEN** возвращается `NotFound`
- **AND** наставник из другой команды либо совпадающий со стажёром приводит к `InvalidArgument`

### Requirement: Конфликты повторного создания

Сервис User SHALL сохранять согласованность существующего профиля при создании стажировки: иной набор ФИО для того же `user_id` и дубликат стажировки с одинаковыми пользователем, командой и датой начала отклоняются как `AlreadyExists`. Повтор Create не является редактированием профиля.

#### Scenario: Дубликат стажировки
- **WHEN** повторно передана уже существующая комбинация пользователя, команды и даты начала
- **THEN** возвращается `AlreadyExists` и дубликат не создаётся

#### Scenario: Попытка заменить ФИО через Create
- **WHEN** у пользователя уже есть профиль с отличающимся ФИО
- **THEN** возвращается `AlreadyExists`, а прежний профиль сохраняется

### Requirement: Чтение метаданных

Сервис User SHALL предоставлять `GetMetadata` и `GET /v1/user/{user_id}/metadata` с профилем стажёра, командой, направлением, датами, плановой длительностью и имеющимися необязательными данными. При нескольких стажировках текущий запрос выбирает запись с наиболее поздней датой начала, затем наибольшим `internship_id`; это правило чтения не задаёт жизненный цикл повторной стажировки.

#### Scenario: Метаданные существуют
- **WHEN** разрешённый клиент запрашивает существующую стажировку
- **THEN** возвращается выбранная запись с ФИО, командой, наставником при наличии и датами в формате `YYYY-MM-DD`
- **AND** фактическая длительность возвращается при наличии фактической даты окончания

#### Scenario: Метаданные отсутствуют
- **WHEN** у указанного пользователя ещё нет стажировки
- **THEN** возвращается `NotFound`, соответствующий HTTP `404`

### Requirement: Права на профиль

Сервис User SHALL требовать пользовательский Bearer access-токен владельца для Create и пользовательского чтения. Доверенный `USER_SERVICE_TOKEN` разрешает чтение метаданных, но не создание профиля. Недоступность Auth не должна разрешать операцию без проверки.

#### Scenario: Собственный профиль и сервисное чтение
- **WHEN** владелец читает свой профиль либо доверенный сервис читает метаданные с сервисным токеном
- **THEN** запрос допускается к обработке

#### Scenario: Чужой пользователь или неподходящий токен
- **WHEN** пользователь пытается создать или прочитать профиль другого `user_id`
- **THEN** возвращается `PermissionDenied`
- **AND** отсутствующий или недействительный access-токен приводит к `Unauthenticated`, а сервисный токен при Create — к `PermissionDenied`

### Requirement: Первичная настройка интерфейса

Frontend SHALL показывать форму профиля только после успешного входа и ответа `404` на запрос метаданных; ошибки доступности не считаются отсутствием профиля. После успешного сохранения профиль перечитывается.

#### Scenario: Аккаунт без профиля
- **WHEN** пользователь вошёл и сервер сообщает, что метаданных нет
- **THEN** открывается форма имени, фамилии, команды и сроков стажировки

#### Scenario: Профиль временно недоступен
- **WHEN** чтение метаданных завершается ошибкой, отличной от `404`
- **THEN** отображаются ошибка и возможность повторной загрузки без создания нового профиля
