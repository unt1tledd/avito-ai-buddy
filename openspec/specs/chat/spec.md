# chat Specification

## Purpose

Обеспечить личные диалоги стажёра с AI Buddy, сохранённую историю и повторяемую отправку вопросов. Chat проверяет пользователя, собирает актуальный контекст для AI и хранит ответы и предложения; правила заявок определены отдельно в access-requests.

## Requirements

### Requirement: Личные диалоги

Сервис Chat SHALL предоставлять создание, список и выбор нескольких диалогов аутентифицированного пользователя. Выбор для отправки и чтения истории передаётся в `X-Conversation-Id` / gRPC metadata `x-conversation-id`; без выбора поддерживается диалог пользователя по умолчанию. ID выбранного диалога должен быть положительным и принадлежать пользователю.

#### Scenario: Создание и выбор
- **WHEN** авторизованный пользователь создаёт диалог и отправляет вопрос с его ID
- **THEN** диалог появляется в его списке, а сообщения сохраняются в выбранном диалоге
- **AND** HTTP-создание возвращает `201`

#### Scenario: Совместимый вызов без выбора
- **WHEN** авторизованный клиент вызывает историю или отправку без ID диалога
- **THEN** используется существующий либо создаётся диалог по умолчанию этого пользователя

#### Scenario: Недоступный диалог
- **WHEN** клиент выбирает чужой, удалённый или недопустимый ID
- **THEN** операция завершается ошибкой без раскрытия чужой истории и без отправки сообщения в диалог другого пользователя

### Requirement: Отправка вопроса и сохранение ответа

Сервис Chat SHALL принимать `POST /v1/chat/messages` / `SendMessage` с текстом и положительным числовым `idempotency_key`, сохранять вопрос и при успешной генерации атомарно сохранять ответ assistant, его источники, предложение при наличии и связь ответа с вопросом. Текст после удаления пробелов по краям должен содержать от 1 до настроенного максимума Unicode-символов; максимум по умолчанию 4000 и не может быть настроен выше 4000.

#### Scenario: Успешный ответ
- **WHEN** действительный запрос обработан зависимостями успешно
- **THEN** возвращается сохранённый `assistant_message` с ID, текстом, временем, источниками и предложением при наличии
- **AND** история содержит вопрос и ответ

#### Scenario: Недопустимый вопрос
- **WHEN** текст пуст после удаления пробелов, превышает настроенный максимум или ключ неположителен
- **THEN** возвращается `InvalidArgument` до сохранения вопроса

#### Scenario: Сбой генерации или сохранения ответа
- **WHEN** после сохранения вопроса возникает ошибка зависимости либо транзакции ответа
- **THEN** клиент получает ошибку без выдуманного успешного ответа
- **AND** вопрос может оставаться в истории, а обработку можно повторить с прежним текстом и ключом

### Requirement: Идемпотентность отправки

Сервис Chat SHALL связывать ключ идемпотентности с диалогом и исходным текстом. Повтор завершённого запроса возвращает сохранённый ответ без новой генерации. Конкурентные повторы не должны создавать несколько вопросов или ответов на один ключ.

#### Scenario: Повтор успешного запроса
- **WHEN** клиент повторяет тот же текст с тем же ключом в том же диалоге
- **THEN** возвращается прежний ответ с тем же ID и новая пара сообщений не создаётся

#### Scenario: Конфликт содержимого
- **WHEN** для ключа сохранён один текст, а повтор содержит другой
- **THEN** возвращается `AlreadyExists` без новой генерации

#### Scenario: Ответ ещё обрабатывается
- **WHEN** конкурентный запрос уже удерживает действующую блокировку обработки вопроса
- **THEN** повтор получает сохранённый ответ, если он готов, либо `Aborted`
- **AND** после завершения обработки повтор возвращает единственный сохранённый ответ

### Requirement: История с курсором

Сервис Chat SHALL предоставлять `GET /v1/chat/messages` / `GetHistory` с `page_size` и `page_token`. Страницы идут от новых сообщений к старым, сообщения внутри страницы возвращаются в хронологическом порядке. Курсор ограничен выбранным диалогом; чтение истории не вызывает AI.

#### Scenario: Чтение по страницам
- **WHEN** клиент последовательно передаёт возвращаемый `next_page_token`
- **THEN** он получает более старые сообщения без повторов между страницами и в конце пустой следующий токен

#### Scenario: История другого пользователя
- **WHEN** другой пользователь читает свой диалог, в котором ещё нет сообщений
- **THEN** возвращается пустая история без сообщений первого пользователя

### Requirement: Проверенная сессия и актуальный контекст AI

Сервис Chat SHALL проверять access-токен через Auth и для новой генерации получать команду и сведения о стажировке из User, контекст треков из Onboarding, передавать AI исходный вопрос и ограниченную историю текущего диалога. В текущем подключённом пути роль actor равна `intern`; браузер не определяет `user_id`, команду и роль actor. Источники прошлых ответов передаются как `history[].source_ids` при корректных сохранённых метаданных.

#### Scenario: Новый вопрос с планом
- **WHEN** генерируется ответ пользователю с назначенным планом
- **THEN** AI получает его проверенный ID, команду, роль, фактическое окончание при наличии и текущие шаги треков
- **AND** история передаётся от старых сообщений к новым без текущего вопроса, максимум 30 сообщений и в пределах настроенного бюджета до 128 КиБ

#### Scenario: Нет плана
- **WHEN** Onboarding успешно возвращает пустой контекст
- **THEN** AI вызывается без выдуманных шагов адаптации

#### Scenario: Сессия не проверена
- **WHEN** access-токен отсутствует или недействителен
- **THEN** возвращается `Unauthenticated`
- **AND** при недоступности Auth возвращается `Unavailable`, операция не выполняется без проверки

### Requirement: Удаление диалогов

Сервис Chat SHALL позволять владельцу удалить один либо все свои диалоги, исключая их из списка и последующего выбора. Текущая операция является логическим удалением, а не обещанием физического стирания данных или отмены заявок Task.

#### Scenario: Удаление своего диалога
- **WHEN** владелец удаляет существующий видимый диалог
- **THEN** HTTP возвращает `204`, диалог исчезает из списка и перестаёт быть доступным для выбора

#### Scenario: Удаление чужого или отсутствующего диалога
- **WHEN** пользователь пытается удалить чужой, отсутствующий или уже удалённый диалог
- **THEN** возвращается `NotFound`, а чужие диалоги не меняются

### Requirement: Уведомления и восстановление состояния

Сервис Chat SHALL предоставлять WebSocket `GET /v1/chat/events` по действительной HttpOnly access-cookie и ограничивать соединение сроком токена. Frontend использует уведомления как сигнал перечитать серверную историю; доставка WebSocket не заменяет сохранённую историю и не обещает воспроизведение пропущенных событий.

#### Scenario: Получение события текущего диалога
- **WHEN** подключённый клиент получает `message.created` для активного диалога
- **THEN** frontend перечитывает историю и объединяет сообщения без повторения сохранённых ID

#### Scenario: Потеря соединения
- **WHEN** WebSocket закрывается, а сессию можно обновить
- **THEN** frontend повторяет подключение и перечитывает историю после открытия
- **AND** истёкшая или отсутствующая access-cookie не позволяет подписаться без повторной проверки сессии
