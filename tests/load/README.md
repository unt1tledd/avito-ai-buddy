# Нагрузочные тесты Chat, AI и Task

Набор предназначен для локального тестового стека Avito AI Buddy. Он создаёт синтетические записи в Auth, User, Chat и Task. Используй отдельный стенд. Запуски оставляют записи в тестовых БД. Сценарии с заглушкой пересоздают контейнер AI, а сценарий восстановления временно останавливает Task. Выполняй прогоны последовательно на одном стенде.

## Установка

Распакуй ZIP из корня репозитория. В архиве уже есть путь `tests/load/`. Старые `chat-history.js`, `chat-history-rate.js`, `run-chat-history.py` и `chat-ai-rate.js` можно сохранить для воспроизводимости прошлых замеров. Новые команды используют `suite.js` и `run.py`.

На машине нужны Bash, Python 3.9+, k6 и Docker Compose. Запусти обычный локальный стек. Для живого AI дополнительно нужны рабочие настройки провайдера и ранее импортированный синтетический корпус. Из корня проверь:

```bash
k6 version
python3 --version
export DOCKER_USE_SUDO=1
sudo docker compose ps auth user onboarding chat ai task kafka db
curl -fsS http://127.0.0.1:8000/readyz
sudo docker compose --profile observability up -d loki alloy prometheus grafana
```

На Mac с Docker Desktop опусти `DOCKER_USE_SUDO=1` и `sudo`.

В Grafana открой **Dashboards → New → Import**, выбери `tests/load/chat-load-dashboard.json` и импортируй с UID `chat-load-suite`. Панели используют текущий Loki с UID `loki`. Если у вас другой UID, укажи его в `make-dashboard.py` и запусти `python3 tests/load/make-dashboard.py` перед импортом. Дашборд поддерживает и старые логи. Оставь поле префикса пустым и выбери время старого запуска вручную.

## Сценарии и команды

| Скрипт | Профиль по умолчанию | Критерий |
|---|---|---|
| `run-history.sh` | 25, 50, 100, 200 GET/с по 2 минуты | 100 аккаунтов, 5 сообщений у каждого. Проверяются содержание, порядок, ID и передача корреляции |
| `run-pagination.sh` | 25, 50, 100 обходов/с по 2 минуты | 100 сообщений на аккаунт. Пять последовательных страниц по 20, проверка курсоров, порядка и повторов. На 100 обходах/с до 500 GET/с |
| `run-ai.sh` | 15, 30, 60 вопросов/мин по 3 минуты | Три класса вопросов, ожидаемый URL источника и наличие вопроса с ответом в истории |
| `run-context.sh` | 30 уточнений/мин, 3 минуты | Подготовленная пара сообщений про pull request и уточнение с отсылкой к предыдущему вопросу |
| `run-mixed.sh` | 100 GET/с и 30 живых вопросов/мин, 5 минут | Сравнить чтение на 100 GET/с с отдельной ступенью истории, пока модель отвечает |
| `run-mock.sh` | 100 GET/с и 60 вопросов/мин, 5 минут | Реальный Chat, AI и поиск через pgvector. Заглушка отвечает быстро или задерживает два этапа на 6 и 9 с. Каждый десятый вопрос повторяется с тем же ключом и проверяется на дубликаты |
| `run-faults.sh` | 60 вопросов/мин, 3 минуты | Чередуются быстрые, медленные, 429, 500 и зависание провайдера. Для заданных отказов проверяются ответ Chat и отсутствие сохранённого ответа ассистента. Для зависания также проверяется нижняя граница ожидания |
| `run-task.sh` | 30, 60, 120 подтверждений/мин, по 2 минуты | Повтор подтверждения, появление заявки в Task, решение, возврат статуса в Chat. Аудит строк Task и смещений двух DLQ |
| `run-recovery.sh` | 60 подтверждений за минуту с выключенным Task, затем проверка восстановления | До старта потребителя заявок в Task нет. После старта ожидаются все заявки и обратные статусы. Проверяются дубликаты строк и рост DLQ |
| `run-soak.sh` | 100 GET/с и 60 вопросов/мин, 30 минут | Повторные вопросы под выделенными сессиями, сохранение ответов, снимки CPU/RAM контейнеров каждые 30 с |

Из корня репозитория, например:

```bash
bash tests/load/run-history.sh
bash tests/load/run-pagination.sh
```

Для AI, User и Task задай ID существующей **тестовой** команды. Узнать его можно через БД User:

```bash
sudo docker compose exec -T db psql -U postgres -d users \
  -c 'SELECT team_id, name FROM users.teams ORDER BY team_id;'
export LOAD_TEAM_ID=1
bash tests/load/run-ai.sh
bash tests/load/run-context.sh
bash tests/load/run-mixed.sh
bash tests/load/run-mock.sh
bash tests/load/run-faults.sh
bash tests/load/run-soak.sh
```

Для Task и восстановления нужен ID тестового пользователя, от чьего имени принимается решение, и токен внутреннего Task API. Возьми фактический токен локального стенда. В Bash можно ввести его без отображения:

```bash
export LOAD_DECIDER_ID=910001  # Пример. Подставь ID своего тестового принимающего решение.
read -rs -p 'TASK_TRACKER_TOKEN: ' TASK_TRACKER_TOKEN
printf '\n'
export TASK_TRACKER_TOKEN
bash tests/load/run-task.sh
bash tests/load/run-recovery.sh
```

Task получает готовые черновики в Chat через SQL, чтобы отдельно замерить подтверждение и Kafka. Он не проверяет, сгенерирует ли AI предложение по политике. Аудит проверяет уникальность сохранённых заявок, а не точное число доставок сообщения самим брокером. DLQ-счётчики относятся ко всему стенду. Для чистой проверки на нём не должно быть другой нагрузки Task. Замер доставки ограничен интервалом опроса до 0,5 с плюс время HTTP-запроса. В восстановлении время видимости считается от начала проверки конкретной заявки после старта Task.

## Полный запуск

После настройки переменных запусти:

```bash
bash tests/load/run-all.sh
```

Полный запуск включает живого провайдера. Профиль задаёт до 555 измеряемых живых вопросов плюс до 13 предварительных. Для обычного ответа часто требуются два вызова LLM, плюс embeddings и возможные повторы. Сверь бюджет и лимиты тестового провайдера перед полным запуском. Для набора только с локальной заглушкой:

```bash
bash tests/load/run-all.sh --offline
```

При неудачной ступени более высокие ступени этого сценария пропускаются. Полный запуск продолжает остальные сценарии и возвращает ненулевой код, если любой из них не прошёл. Длительность полного профиля больше часа с учётом подготовки. Для отдельного сценария можно переопределить интенсивность и длительность. Например, повторить уже проблемную ступень AI без повышения:

```bash
bash tests/load/run-ai.sh --rates 15 --seconds 180
```

Для истории и пагинации `--rates` задаёт итерации в секунду. Для вопросов и заявок — в минуту. Для смешанных профилей `--history-rps` меняет интенсивность чтения. Для короткой проверки установки:

```bash
bash tests/load/run-history.sh --rates 25 --seconds 10
```

## Отчёт и Grafana

Каждый запуск печатает URL и сохраняет оглавление в `~/k6-reports/chat-suite-…/index.html`. Открой его в браузере.

1. **Весь набор** показывает общую серверную картину за время запуска.
2. **Ступень** открывает серверные графики только по её запросам. Отчёт ступени содержит ссылки на все её тестовые аккаунты.
3. **Аккаунт** фильтрует записи по префиксу этого аккаунта в данной ступени. В панели журналов можно раскрыть любой запрос и увидеть его полный `request_id`.
4. **summary.txt** — компактная таблица с числом проверок, p50/p95/p99 и причинами ошибок. `metrics.json` — исходные точки k6. `events.log` — события с ID запросов, а для Task ещё и ID заявки. `k6.log` — полный вывод k6 с порогами.

Дашборд собирает графики из Loki. Логи сервисов без переданного ID, в том числе асинхронные операции Kafka, могут отсутствовать при фильтрации по аккаунту. Для них используй ID заявки или предложения из `events.log` и журнал Task за тот же интервал. Клиентские результаты k6 остаются в файлах. Prometheus не требует правок.

В отчёте количество отказов включает функциональные ошибки, например неожиданный источник при HTTP 200. В сценарии с намеренными отказами корректный ответ Chat на инъекцию считается успешной проверкой. p95 по шагу включает все наблюдавшиеся результаты этого шага, поэтому читай его вместе с таблицей ошибок и разбивкой по классу. Пороги на SLO задержки команда ещё не задала. Успех означает прохождение проверок, достижение минимального запланированного количества операций и отсутствие пропущенных k6 итераций.

## Восстановление стенда

В штатном ходе сценарий заглушки восстанавливает AI с основным Compose-файлом, а recovery поднимает Task в блоке очистки. Если процесс был принудительно завершён, из корня выполни:

```bash
sudo docker compose up -d --no-deps ai task
sudo docker compose -f docker-compose.yml -f tests/load/compose.mock.yml stop load-provider load-db
```

Проверка установки начинается с короткого прогона истории, затем AI и Task по одному. Так видно, какой маршрут, схема или поле расходится с текущей веткой. Код сверялся с доступными диффами, поэтому именно первый запуск на вашем Compose проверяет фактическую совместимость.
