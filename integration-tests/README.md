# Интеграционные тесты aiBody

Запуск из корня проекта (нужен запущенный Docker Desktop / Docker Engine с Compose):

```sh
make integration-test
# или
task integration-test
```

Каждый запуск создаёт отдельный Compose-проект без опубликованных портов и без
использования рабочего `.env`. PostgreSQL хранит данные в tmpfs. После завершения,
в том числе при ошибке теста, скрипт удаляет только свой стенд. При ошибке выводятся
логи сервисов, код возврата тестов сохраняется. Прерванный через SIGKILL запуск
может потребовать ручного удаления проекта `aibody-it-*`.

Работают настоящие auth, user, chat, task, onboarding, PostgreSQL и Kafka.
Только внешний AI заменён фиксированным HTTP-ответом: это проверка интеграции
сервисов, а не качества LLM/RAG. User загружает штатные демонстрационные команды
и наставников; аккаунты и стажировки тесты создают через публичные API.

Проверяется:

- Auth: регистрация, вход, refresh-cookie, проверка владельца токена, запрет
  подмены access/refresh, ошибки входных данных и конкурентная регистрация.
- User: создание по gRPC и чтение по HTTP, сохранение профиля/команды/наставника,
  дубликаты, некорректные даты и ссылки, успешный повтор после отклонённого создания.
- Chat: сохранённая история, постраничное чтение без дублей, изоляция пользователей,
  повтор запроса с тем же ключом, конфликт ключа и конкурентные повторы.
- Tasks: чужое предложение нельзя подтвердить; повторное подтверждение создаёт
  одну задачу; решение ограничено командой; одобрение и отказ проходят через
  Kafka обратно в историю чата; повтор решения идемпотентен; конкурирующие решения
  имеют ровно одного победителя; HTTP/gRPC требуют tracker credentials.

Тесты проверяют конкретные статусы и значения. Ошибка доступности стенда приводит
к падению, а не к пропуску. Для асинхронной доставки используются ограниченные
ожидания условия. Тесты намеренно последовательны; конкурентность включена только
в сценариях гонок. Данные живут до удаления изолированного стенда; глобального
TRUNCATE и очистки пользовательских БД нет.

## Auth — регистрация и токены
1. TestAuthLifecycle — регистрирует пользователя, входит в аккаунт и проверяет, что access-токен принадлежит этому пользователю. Повторная регистрация должна вернуть 409, неверный пароль — 401. Затем тест проверяет HttpOnly и путь refresh-cookie, запрет подмены access- и refresh-токенов и получение нового access-токена для того же пользователя.
2. TestAuthInvalidInput — проверяет пять ошибок. Некорректный email, короткий пароль и пустые данные для входа дают 400. Невалидный токен и запрос на обновление без refresh-cookie дают 401.
3. TestConcurrentRegistrationCreatesOneAccount — одновременно отправляет четыре запроса на регистрацию с одним email. Ровно один должен получить 201, остальные — 409. Затем тест проверяет, что в созданный аккаунт можно войти.
## User — профиль стажёра
4. TestUserPersistsAcrossGRPCAndHTTP — создаёт стажировку по gRPC и проверяет сохранённые данные профиля, команды, наставника и сроков. Читает профиль через HTTP и сравнивает ответы двух интерфейсов. Повторное создание должно вернуть AlreadyExists.
5. TestUserInvalidCreationDoesNotPersist — пытается создать стажировку с несуществующей командой, наставником из другой команды, невозможной датой или окончанием раньше начала. После каждой ошибки стажировка должна отсутствовать. Повтор с корректными данными и другим именем должен пройти — так тест ловит и частично сохранённый профиль.
## Chat — история и повторные запросы
6. TestChatHistoryIdempotencyAndIsolation — повтор отправки с тем же текстом и ключом возвращает сохранённый ответ. Другой текст с тем же ключом вызывает конфликт. Второй пользователь не видит чужую историю и может использовать тот же ключ в своём чате. Тест также собирает историю по страницам и сверяет её с полной выдачей и ответом HTTP.
7. TestChatRejectsUnauthorizedAndInvalidMessages — проверяет, что историю нельзя прочитать без токена или с неверным токеном через HTTP и gRPC. Сообщение из пробела и сообщение с нулевым ключом отклоняются, история остаётся пустой.
8. TestConcurrentMessageRetriesSaveOnePair — одновременно отправляет шесть одинаковых сообщений с одним ключом. Запросы либо получают один и тот же ответ, либо получают Aborted, пока ответ готовится. В истории должна остаться ровно одна пара из вопроса и ответа.
## Tasks — заявки на доступ
9. TestAccessRequestLifecycle — проверяет путь от предложения в чате до заявки в Tasks и уведомления обратно в чат через Kafka. Другой пользователь не может подтвердить предложение, повторное подтверждение создаёт одну заявку, а решение от другой команды отклоняется. Тест отдельно прогоняет одобрение и отказ. В обоих случаях заявка уходит из списка ожидающих, такой же повтор решения возвращает сохранённый результат, а изменённое решение вызывает конфликт.
10. TestConcurrentTaskDecisionsHaveOneWinner — одновременно одобряет и отклоняет одну заявку. Ровно одно решение должно сохраниться, второе получает AlreadyExists. Повтор победившего запроса возвращает сохранённое решение.
11. TestTaskAuthorizationAndValidation — проверяет, что список задач недоступен без корректного tracker-токена через HTTP и gRPC. Нулевой ID команды отклоняется, а команда без заявок получает пустой список [].

      




Выбор одного сценария:

```sh
bash integration-tests/run.sh go test -tags=integration -race -count=1 -timeout=10m -v -run TestAccessRequestLifecycle ./...
```

Проверка компиляции без стенда (не выполняет сценарии):

```sh
cd integration-tests
go test -tags=integration -race -run '^$' ./...
go vet -tags=integration ./...
```

Тег `integration` отделяет эти тесты от обычного `make test`.
`TEST_AUTH_URL`, `TEST_USER_URL`, `TEST_CHAT_URL`, `TEST_TASK_URL` и
`TEST_USER_GRPC`, `TEST_CHAT_GRPC`, `TEST_TASK_GRPC` позволяют переопределить адреса.
Внешний стенд должен быть выделенным тестовым окружением с теми же fixtures,
тестовыми токенами и AI-заглушкой; сценарии создают данные и принимают решения.
