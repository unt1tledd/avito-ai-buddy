# Гибридный поиск и переиндексация

`find_instruction` и HTTP-контракт не изменены. Основная LLM по-прежнему формирует запрос перед поиском; действуют прежние дедлайн, до трёх вызовов инструмента, проверка цитат и стандартный ответ `no_knowledge`. Ошибка поиска остаётся технической ошибкой, а не отсутствием знаний.

## BM25, pgvector и RRF

Зависимость — существующий PostgreSQL 16 с pgvector; новых Python-пакетов и замены общего образа БД нет. BM25 реализован явно в SQL через таблицу `chunk_terms` с инвертированным индексом `(term, chunk_id)`, точными частотами, длиной и IDF. Это настоящий Okapi BM25, **не `ts_rank`**:

```text
BM25(d,q) = Σ ln(1 + (N-df(t)+0.5)/(df(t)+0.5))
                × tf(t,d)×(k1+1) / (tf(t,d)+k1×(1-b+b×dl(d)/avgdl))
```

`k1=1.2`, `b=0.75`. Положительный вариант IDF соответствует [описанию Lucene BM25Similarity](https://lucene.apache.org/core/10_3_1/core/org/apache/lucene/search/similarities/BM25Similarity.html). Статистика `N`, `df`, `avgdl` вычисляется **только на доступном корпусе активного профиля и версии подготовки**. Закрытые документы не влияют на ранги открытых.

`knowledge_terms` использует [PostgreSQL ts_debug](https://www.postgresql.org/docs/16/textsearch-debugging.html) с явной конфигурацией `pg_catalog.russian`: русские слова проходят встроенный стемминг; термы с ASCII-буквами/цифрами сохраняются в нижнем регистре без английского стемминга. Дефисные слова дают как составной терм, так и части согласно парсеру PostgreSQL. Это не исправление опечаток, не синонимизация и не полная лемматизация: переформулирование остаётся у LLM. Считаются все вхождения, без ограничения tsvector в 256 позиций одного терма. Проверены формы «заявка/заявками», `AUTH-403`, `pg_stat_statements`, `OAuth2`, `Qwen3-Embedding-8B`, URL и VPN.

`pg_search`/ParadeDB рассматривался как расширение BM25. Для нынешнего лимита 4000 чанков выбран проверяемый SQL на уже используемом образе pgvector: это не требует установки стороннего бинарного расширения в общую БД других сервисов. Цена выбора — точное сканирование доступного корпуса для статистик/векторов. При росте корпуса следует измерить нагрузку и перейти на совместимое расширение, сохранив ACL **до** top-k и транзакционное переключение. Это не ANN и не обещание масштабирования до миллионов документов.

Один SQL-запрос использует один MVCC-снимок. Материализованный `eligible` применяет роль, команду, `embedding_profile` и `text_preparation_version` до обеих веток. Независимо выбираются top-10 BM25 и top-10 pgvector; порог `KNOWLEDGE_MIN_SIMILARITY` действует только на векторную ветку. BM25-кандидат проходит даже при нулевой/отрицательной cosine similarity. Далее:

```text
RRF(source_id) = bm25_weight/(k+bm25_rank) + vector_weight/(k+vector_rank)
```

Отсутствующая ветка даёт нулевой вклад; ранги начинаются с 1, `k=60`, веса равны 1. Используется вещественное деление. Результаты объединяются по `source_id`, итог — top-3; равенства разрешаются по `source_id COLLATE "C"`. RRF не вероятность: порога RRF нет, score не передаётся модели/клиенту. Даже непустая выдача может закончиться `no_knowledge`, если исходные фрагменты не содержат ответа.

## Подготовка текста и атомарный импорт

Сначала выполняется существующее разбиение с прежними ID и перекрытием. Для каждого чанка LLM получает **полный исходный документ**, заголовок/ключевые слова, исходный чанк и номер части. Системная инструкция определяет эти поля как недоверенные данные, запрещает выполнять вложенные инструкции и добавлять факты. Возвращаются 1–3 предложения, до 600 символов. Вызовы выполняются только CLI-импортером.

В БД раздельно сохраняются:

- `documents.original_body`, `documents.keywords` — полный документ и метаданные издателя;
- `document_chunks.body` — неизменный исходный чанк;
- `document_chunks.generated_context` — пояснение LLM;
- `document_chunks.search_text` — `title + keywords + generated_context + body`, разделённые переводами строк. Один и тот же текст идёт в embeddings и BM25.

Поиск возвращает только `body`, прежние ID, заголовок, URL и разрешённые метаданные политики. Generated context не попадает в инструменты модели ответа, цитаты, публичные sources или историю; он не может подтверждать факты/права.

До записи в БД должны завершиться **все** контекстуализации и все пакеты embeddings. Ошибка/таймаут/пустой или слишком длинный контекст отменяет импорт; fallback на часть корпуса отсутствует. TaskGroup отменяет остальные вызовы. Затем одной транзакцией с прежней блокировкой заменяются документы, ACL, embeddings, контексты и postings; подсчитываются длины. Ошибка postings также откатывает всю замену. Читатель видит предыдущий или новый целый снимок. Параллельные импорты сериализуются при записи; последний commit побеждает. Кеш может содержать успешно подготовленные элементы неудавшегося импорта — действующий индекс это не меняет.

SQLite-кеш адресуется хешем полного документа, чанка, позиции, заголовка, keywords, текста и версии промпта, URL и модели LLM. Ключей API, ACL и сырого промпта в нём нет; значения содержат производные знания. Файл получает права 0600. Одинаковые запросы объединяются внутри одного импорта; между процессами кеш безопасен, но одновременный промах может вызвать повторную генерацию. Лимит параллелизма действует на один процесс импорта. Кеш нельзя публиковать; в Compose он хранится в `ai_context_cache`. После смены провайдера/модели/версии промпта кеш автоматически разделяется. Удаление кеша допускается при остановленных импортерах и увеличивает стоимость следующего импорта.

`TEXT_PREPARATION_VERSION=hybrid-text-v1` версионирует поля, порядок, chunking и токенизацию. Меняя любой из них, нужно увеличить константу. Хеш профиля дополнительно включает включённость контекстуализации, модель/endpoint LLM, текст и версию промпта. Поэтому старые embeddings, контекстный и бесконтекстный корпуса не смешиваются. Смена `RETRIEVAL_MODE`/RRF не меняет подготовленный индекс. Для изменения модели за прежним URL увеличивается `EMBEDDING_INDEX_VERSION`. Старые строки миграция сохраняет без backfill; новый читатель отклоняет неподготовленный/смешанный профиль с `reindex_required` или несовпадающий профиль с `profile_missing`.

## Конфигурация

| Переменная | Начальное значение | Назначение |
|---|---:|---|
| `RETRIEVAL_MODE` | `hybrid` | `hybrid` или `vector` для диагностики |
| `SEARCH_CANDIDATES` | 10 | top-k каждой ветки, 1–100 |
| `SEARCH_TOP_K` | 3 | итоговые источники, 1–3 в рамках текущих лимитов агента |
| `RRF_K` | 60 | знаменатель RRF |
| `RRF_BM25_WEIGHT`, `RRF_VECTOR_WEIGHT` | 1 | положительные веса |
| `BM25_K1`, `BM25_B` | 1.2 / 0.75 | насыщение частоты и нормализация длины |
| `CONTEXTUALIZATION_ENABLED` | `true` | при `false` нужен отдельный полный импорт и одинаковая настройка у сервера |
| `CONTEXT_PROMPT_VERSION` | `chunk-context-v1` | версия промпта, часть профиля и ключа кеша |
| `CONTEXT_TIMEOUT_SECONDS` | 25 | дедлайн одного LLM-вызова, включая чтение ответа |
| `CONTEXT_CONCURRENCY` | 4 | максимум одновременных контекстуализаций на импортер |
| `CONTEXT_MIN_INTERVAL_SECONDS` | 0 | минимальный интервал запуска LLM-вызовов; для ограниченного RPM, например 3 с |
| `CONTEXT_CACHE_PATH` | `.data/context-cache.sqlite3` | постоянный локальный кеш |
| `IMPORT_TIMEOUT_SECONDS` | 900 | дедлайн всего импорта |

Embeddings по-прежнему идут пакетами до 32, HTTP timeout 25 с; запись БД ограничена 30 с, поиск — 3 с. Общий импорт не повторяет автоматически HTTP 429: исправьте лимит/повторите позже; подготовленные контексты переиспользуются. Для контекстуализации требуются `LLM_MODEL`, `LLM_API_KEY`, `LLM_BASE_URL`; embeddings используют свой прежний профиль. Существующий `KNOWLEDGE_PROCESSING_APPROVED` продолжает требоваться до передачи корпуса.

## Обновление и запуск

Остановите старые AI-процессы и импортеры, сохраните резервную копию схемы/данных. Миграция `000004_hybrid_search.sql` не перезаписывает корпус. Не запускайте старый сервер после импорта нового профиля. В рабочей БД расширение pgvector должно быть установлено DBA; в тестовой БД устанавливайте его в `public` до создания временных схем.

Из корня репозитория, с заполненным `.env` и согласованными настройками сервера/импортера:

```sh
docker compose -p ai-rag-check up --wait db
docker compose -p ai-rag-check build ai
docker compose -p ai-rag-check --profile tools run --rm ai-migrate
docker compose -p ai-rag-check run --rm ai \
  /app/.venv/bin/python -m ai_service.rag.import_documents /app/knowledge/documents.json
docker compose -p ai-rag-check run --rm -d --name ai-rag-check-api \
  -p 127.0.0.1:18000:8080 ai
curl --fail http://127.0.0.1:18000/readyz
```

Импорт печатает JSON: профиль, число документов/чанков, время, вызовы, cache hits, input/output tokens и полноту телеметрии. Стоимость в валюте определяется тарифом провайдера, не RRF и не числом символов. При отсутствии usage нельзя выдавать ноль за измеренную стоимость.

После успешного `/readyz` выполните разрешённый и запрещённый запрос с настоящими профилями ACL. Возврат к другой конфигурации требует полного переимпорта. Down миграции 000004 запрещён, пока есть новые подготовленные строки; для возврата к старому приложению восстанавливайте сделанную до обновления резервную копию схемы и данных.

## Воспроизведение проверки

```sh
cd ai
AI_TEST_POSTGRES_DSN='postgresql://.../disposable_test_db' uv run --locked pytest -q
AI_TEST_POSTGRES_DSN='postgresql://.../disposable_test_db' \
  uv run --locked python tests/benchmark_search.py
# Внешние вызовы, бюджет и передача содержимого провайдерам:
AI_TEST_POSTGRES_DSN='postgresql://.../disposable_test_db' \
  uv run --locked --env-file ../.env python tests/eval_hybrid_search.py --live \
  --output evals/hybrid-search.json
```

Сравнение использует одни и те же 144 документа и 305 вопросов: 288 answerable, 9 insufficient_knowledge, 8 restricted_source. Baseline воспроизводит старый SQL и старый порядок embedding text; гибрид без контекста и с контекстом используют текущую подготовку. Каждая ветка получает отдельную временную схему; рабочие таблицы не заменяются. Recall@3 — доля ожидаемых источников в top-3, MRR@3 — обратный ранг первого правильного источника. Эти метрики используют исходные вопросы без LLM-переформулирования, чтобы изолировать retrieval. `no_knowledge` проверяется через настоящий Agent с переформулированием и цитатами; строгий успех — точный стандартный ответ и пустые sources. Ответ «ссылка не указана» с цитатой считается отдельным исходом, а техническая ошибка — недоступной проверкой, не отказом от выдумки.

Задержка retrieval — SQL через прогретый пул, без embeddings/LLM; время полного ответа измеряется отдельно на insufficient_knowledge. Импорт измеряется фактически, с числом новых вызовов и cache hits. Для оценки в USD передайте актуальные тарифы за миллион токенов: `--llm-input-usd`, `--llm-output-usd`, `--embedding-usd`; без тарифов или полного usage значение `null`. Это оценка, не списание из биллинга. Частичные результаты и технические ошибки сохраняются в JSON. `--modes hybrid_context` повторяет только выбранный режим и сохраняет другие результаты в том же отчёте при совпадении хешей набора. Для ограниченного RPM задайте `CONTEXT_CONCURRENCY=1 CONTEXT_MIN_INTERVAL_SECONDS=3`; импорт займёт больше времени. Итоги первого прогона: [hybrid-search-results.md](hybrid-search-results.md).
