# Сценарий · Настройка окружения

Стажёр backend-команды спрашивает, как настроить окружение. AI-buddy находит тестовую инструкцию и объясняет шаг. После подтверждения стажёром AI-buddy отмечает шаг выполненным и возвращает сохранённый статус.

| Условие | Ожидаемое поведение |
|---|---|
| Стажёр спрашивает об окружении | Агент вызывает `find_instruction` и возвращает ответ с доступным источником. |
| Подходящего документа нет среди разрешённых | Поиск возвращает пустой список. В ответе сообщается, что доступных сведений недостаточно. |
| Найдена памятка с другой ролью или командой | Её фрагмент не попадает в контекст модели и ответ API. |
| Стажёр подтвердил `dev-environment` | AI-buddy передаёт подтверждённый ID в `onboarding`. Сервис адаптации проверяет права, сохраняет статус и возвращает `completed`. |
| Подтверждения нет | Вызова записи нет. |
| Сервис отклоняет действие | AI-buddy сообщает об отказе. В ответе API `action` равен `null`. |
| SQLite получает повторное подтверждение того же шага | AI-buddy возвращает существующий статус. Тестовая база хранит одну запись на пару пользователь–шаг. |
| Модель или поиск недоступны | Для подтверждённого шага AI-buddy обрабатывает результат `onboarding` напрямую. |
| После отправки запроса истёк таймаут | AI-buddy сообщает о неизвестном результате с `action: null`. Автоматического повтора записи нет. |

Идентификатор пользователя и подтверждение передаёт авторизованный сервис `chat`. В интеграции AI-buddy получает актуальный профиль из `user`. Сервис `onboarding` владеет состоянием шага и проверяет право на изменение. Модели доступен инструмент поиска `find_instruction`.

## Межсервисный контракт

- Оба пути, `POST /api/v1/chat` и `POST /v1/chat`, принимают один и тот же Bearer-токен `AI_SERVICE_TOKEN`. В интеграции `chat` передаёт `conversation_id` и положительный `int64` в `actor.user_id` как десятичную строку. Переданные поля `actor.role` и `actor.team` используются только в деморежиме. `history` длиной до 12 сообщений принимается для совместимости и не передаётся модели.
- Для вопросов AI читает `GET /v1/user/{user_id}/metadata` с `USER_SERVICE_TOKEN`. Контракт проверен с gateway ветки `feat/user` на `5ebe41b`. Из подтверждённой записи `intern` AI выдаёт только ACL-роль `intern`. При наличии `actual_end_date` профиль для RAG отклоняется. Ключ команды — строковое `team.team_id`. Для других ролей нужен явный авторитетный источник прав от владельца профиля. Корпус для интеграции указывает реальные ID команд, а комплектный корпус с символьными ID команд предназначен для демо.
- Gateway `5ebe41b` возвращал профиль с HTTP 200 при верном, неверном и отсутствующем Bearer. Перед интеграцией владелец `user` должен проверять токен на gateway или предоставить закрытый gateway с проверкой сервисной идентичности и без прямого доступа к HTTP и gRPC из недоверенной сети. Приёмочный тест ожидает 401/403 для отсутствующего и неверного токена, 200 для верного токена и существующего пользователя, 404 для отсутствующего профиля. Ожидаемые поля успешно проверены через реальный gateway с PostgreSQL.
- Явное `confirmed_step_id` на запросе от авторизованного `chat` обрабатывается отдельно от поиска. AI делает одну попытку `PUT /v1/users/{user_id}/onboarding/steps/{step_id}/completion` с `ONBOARDING_SERVICE_TOKEN`. Владелец `onboarding` должен проверить токен, авторизовать пользователя для указанного шага и вернуть `200 {"step_id":"…","status":"completed"}` только после сохранения. Контракт отказа — 403/404. Проверяемые отказы записи и неизвестный результат возвращают `action: null`. Сбой соединения до отправки или 401 от `onboarding` возвращает 502. После отправки потерянный или неоднозначный результат возвращает 200 с сообщением о неизвестном исходе. Повторной записи со стороны AI нет.
- В `feat/chat-service` на `402b9cc` адаптеры AI, профиля и onboarding возвращают `ErrUnsupported`, а реализация записи отсутствует в доступном `onboarding`. В сквозном тесте `chat` должен брать ID из проверенной сессии, проверять принадлежность разговора и передавать явное подтверждение. `onboarding` должен отклонять чужой шаг и неверный сервисный токен, а при остановленном `user` сохранять разрешённый шаг. При потере ответа после записи нужно подтвердить одну попытку PUT и неизвестный исход в AI.

## Запуск, данные и готовность

`/healthz` проверяет, что процесс отвечает. `/readyz` возвращает 503 с кодом причины при отсутствии обязательной конфигурации, недоступной схеме PostgreSQL или отсутствии активного профиля индекса. При `CONFIRMATIONS_ONLY=true` readiness проверяет конфигурацию для подтверждений, а вопросы по базе знаний получают 503. Этот режим не требует PostgreSQL, LLM или настроек `user`. Некорректная конфигурация режима или адреса поставщика отклоняется при старте.

По умолчанию на приём и обработку chat-запроса выделяется 15 секунд. `CHAT_TIMEOUT_SECONDS` допускает значения до 25 секунд, чтобы оставить время клиенту `chat` с HTTP-бюджетом 30 секунд. Прокси должен иметь таймаут выше дедлайна AI. Максимум входного тела — 256 КиБ. На запрос возможны начальный поиск и до трёх вызовов инструмента, с переиспользованием нормализованных запросов внутри текущего профиля. Диагностика содержит операцию, причину, длительность и `X-Request-ID` без содержимого запроса и секретов.

Сервис передаёт LLM текущий вопрос, фрагменты с действующим ACL и результаты вызовов инструмента. Embeddings получает запрос и тексты импортируемого корпуса. Сведения из профиля, переписка и чужие по ACL документы исключены из справочного контекста. Перед включением `KNOWLEDGE_PROCESSING_APPROVED=true` владелец развёртывания подтверждает допустимость корпуса, вопросов и обоих получателей по политике проекта. Политика поставщиков и разрешения на реальный корпус проверяются при развёртывании. Live-проверка использовала синтетический текст. Контекст ограничен 64 КиБ сериализованных данных, ответ содержит до шести источников, до 1200 символов на фрагмент и до 18 КиБ данных источников. Маркеры `[source:ID]` проверяются по фрагментам, переданным в текущем запросе.

### Профили и переиндексация

Обычный профиль хранит 1536 измерений. Для прямого SiliconFlow используются `EMBEDDING_BASE_URL=https://api.siliconflow.com/v1`, `EMBEDDING_MODEL=Qwen/Qwen3-Embedding-8B`, отдельный `EMBEDDING_API_KEY` и 1024 измерения. Для проверенного варианта на 1536 используются `EMBEDDING_BASE_URL=https://openrouter.ai/api/v1`, `EMBEDDING_MODEL=qwen/qwen3-embedding-8b`, `EMBEDDING_PROVIDER=deepinfra` и отдельный ключ OpenRouter. OpenRouter получает фиксированного поставщика без fallback. Настройки LLM отдельные. [SiliconFlow Embeddings](https://docs.siliconflow.com/cn/api-reference/embeddings/create-embeddings#body-dimensions) · [OpenRouter Embeddings](https://openrouter.ai/docs/api/api-reference/embeddings/submit-an-embedding-request)

Профиль индекса включает URL embeddings, поставщика за маршрутизатором, модель, размерность и `EMBEDDING_INDEX_VERSION`. При замене модели или поставщика либо изменении пространства векторов за прежним URL нужно применить настройки импорта и рантайма согласованно и переиндексировать корпус. Для изменения за прежним URL и с тем же именем модели увеличивается `EMBEDDING_INDEX_VERSION`. Старые векторы без профиля сохраняются миграцией, но поиск по ним не выполняется.

1. Остановите старый AI и импорт перед переключением. Сохраните резервную копию отдельной базы знаний или её схемы, затем примените миграции в базе с установленным pgvector.
2. Запустите импорт с целевыми настройками. Файл содержит от 1 до 1000 фрагментов, занимает до 4 МиБ и содержит до 4000 символов текста на фрагмент. Импорт подготавливает все векторы, затем атомарно заменяет **весь** корпус. Ошибка сохраняет предыдущий снимок. Параллельные замены сериализуются, итоговый снимок принадлежит последней зафиксированной транзакции.
3. Проверьте `/readyz` и тестовый запрос с разрешённой и запрещённой ACL. Для возврата на другой профиль в новой схеме переимпортируйте прежний корпус с его настройками. Для возврата на старую версию приложения восстановите резервную копию схемы и данных, сделанную до миграции. `goose down` миграции 3 допускается только при отсутствии векторов с новым профилем, что защищает старый поиск по одному имени модели.

```sh
cd ai
goose -dir migrations postgres "$KNOWLEDGE_DB_DSN" up
uv run --locked python -m ai_service.rag.import_documents knowledge/documents.json
uv run --locked uvicorn ai_service.main:create_app --factory --port 8080
```

MCP — библиотечный адаптер для in-process клиентов с уже проверенным `Actor`. В поставляемом HTTP-сервисе используется тот же `Retriever`. `sql/chat_profiles.sql` остаётся для совместимости со старым стеком `infra/local-stack`, где DDL подключён в README и runtime читает таблицу. Текущий AI получает профиль из `user`.

## Воспроизведение проверок

```sh
cd ai
uv lock --check --offline
AI_TEST_POSTGRES_DSN=... uv run --locked pytest -ra --cov=ai_service
AI_TEST_POSTGRES_DSN=... uv run --locked python tests/benchmark_search.py
docker build -t avito-ai:verify .
docker run --rm -p 127.0.0.1:8080:8080 -e AI_MODE=demo \
  -e CONFIRMATIONS_ONLY=true -e AI_SERVICE_TOKEN=smoke avito-ai:verify
```

Тесты PostgreSQL создают отдельные схемы и требуют установленного pgvector в тестовой базе. Проверены ACL, порог, порядок, отсутствие профиля, смена версии, конкурентные импорты, откат при ошибке импорта и защитный отказ при downgrade. Benchmark печатает `EXPLAIN (ANALYZE, BUFFERS)` и задержки 100 запросов через прогретый пул на каждый вариант. PostgreSQL 16.13 и pgvector 0.8.2, loopback, векторы 1536, корпус синтетический.

| Фрагменты | Доступно по ACL | p50, мс | p95, мс | EXPLAIN Execution Time, мс |
|---:|---:|---:|---:|---:|
| 100 | 90% | 0,76 | 0,90 | 1,021 |
| 100 | 1% | 0,36 | 0,43 | 0,114 |
| 100 | 0% | 0,31 | 0,33 | 0,095 |
| 1000 | 90% | 5,61 | 7,21 | 6,509 |
| 1000 | 1% | 1,68 | 1,83 | 1,465 |
| 1000 | 0% | 1,70 | 2,30 | 1,427 |

Пул использует до четырёх соединений, до 16 ожидающих и ожидание выдачи до двух секунд. Точный top-3 сохранил порядок и полноту после фильтрации. При максимальном размере поддерживаемого импорта локальный p95 составил 7,21 мс, поэтому ANN-индекс не добавлялся. Измерения исключают внешние запросы и не заменяют замеры под нагрузкой в целевом стеке.

В полном прогоне на PostgreSQL прошли 139 тестов, покрытие строк 96%. Контрактный тест сравнивает сохранённый OpenAPI со схемой приложения. В чистой production-установке Python 3.12.14 прошли `/readyz` и подтверждения через оба HTTP-пути. Сборка и запуск Docker-образа требуют среды с Docker. Живой импорт и поиск с синтетическим фрагментом прошли на OpenRouter/DeepInfra с 1536 измерениями. Для прямого SiliconFlow проверены документированный размер, запрос и путь импорта и поиска с подменённым HTTP-транспортом. Для live-проверки нужен ключ SiliconFlow.
