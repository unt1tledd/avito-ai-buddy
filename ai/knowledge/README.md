# Синтетическая база знаний «Авито Вики»

Готовый набор для наполнения RAG-базы AI-buddy: **45 статей, 5 разделов, 15 подразделов, 99 проверочных сценариев**. Все сведения вымышлены. Набор не подтверждает реальные правила, адреса, льготы, выплаты или сервисы Авито.

## Файлы

| Файл | Назначение |
|---|---|
| `documents.json` | JSON-массив, совместимый с `ai_service.schemas.contracts.Document`; только этот файл подаётся импортеру |
| `knowledge.md` | Полная читаемая база с иерархией, правами и примерами вопросов |
| `eval_cases.json` | 90 вопросов с эталонами, 6 проверок нехватки знаний и 3 проверки прав |
| `manifest.json` | Структура, версия, количество статей и обозначения ролей |
| `README.md` | Условия использования, импорт и проверка |

Прежний корпус из двух тестовых документов сохранён отдельно в `demo-documents.json`. Основной файл `documents.json` содержит новый корпус из 45 статей.

## Содержание

1. Новичкам: доступы; офис; льготы.
2. Как устроен офис: что где лежит; правила; переговорки.
3. Организация рабочего места: рабочее место; почта; техника.
4. Зарплаты и льготы: зарплата; бонусы; ДМС.
5. Коммуникации: корпоративная связь; почта; встречи.

На каждый подраздел приходится три самостоятельных документа. Они содержат адрес действия, шаги, ограничения, срок, критерий результата и контакт поддержки, где это применимо. Повторяющиеся сведения согласованы: питание 450 ₽ за день посещения, выплаты 5-го и 20-го, ДМС с 31-го дня, спорт с начала второго календарного месяца. Все суммы и условия демонстрационные.

## Формат и права

Каждая запись содержит `id`, `title`, `url`, `text`, `roles`, `teams`, `keywords`. `text` вместе с отметкой «сведения вымышлены» короче 1200 символов: текущий поиск AI возвращает первые 1200 символов фрагмента. Эмбеддинги не подделаны и не включены: их создаёт штатный импорт с выбранным провайдером.

Общие статьи доступны `intern` и `mentor`. Только `mentor` доступны:

- `synth-mentor-onboarding-check` — проверка первого дня;
- `synth-mentor-bonus-review` — подготовка итоговой оценки;
- `synth-mentor-one-on-one` — встречи наставника со стажёром.

`teams=[]` означает отсутствие командных ограничений. Имя Demo Backend — часть вымышленного содержания одной статьи, а не ACL. ID команды `101` в eval — произвольный тестовый ID. Текущий интеграционный адаптер AI выдаёт только роль `intern`: три проверки `mentor` требуют деморежима или отдельного согласованного источника прав.

`knowledge.md` и `eval_cases.json` содержат закрытые статьи и эталоны целиком и предназначены владельцу корпуса. В RAG нужно загружать `documents.json` с сохранением ролей. Не передавайте весь Markdown пользователю-стажёру или в модель в обход фильтрации.

Адреса `*.avito.example`, почтовые ящики в `.example`, страховщик «ДемоСтрах», город Примерск и адрес Тестовая, 10 вымышлены. Ссылки служат идентификаторами источников; веб-страницы не созданы. Персональных зарплат, реальных паролей, настоящих контактов и учётных данных в наборе нет.

## Импорт в существующий ai-service

Набор пока НЕ загружен в БД. Импорт вызывает embeddings API и затем **атомарно заменяет весь существующий корпус**, включая прежние демостатьи. До импорта сохраните нужные прежние данные. Не объединяйте автоматически этот синтетический корпус с реальными правилами компании.

1. Подготовьте отдельную демобазу PostgreSQL с pgvector и примените обе актуальные миграции из `ai/migrations`. Для ранее созданной вручную базы без учёта версий Goose нужна отдельная процедура обновления; не запускайте вслепую первую миграцию поверх существующих таблиц.
2. Укажите `KNOWLEDGE_DB_DSN`, настройки embeddings и `KNOWLEDGE_PROCESSING_APPROVED=true` после одобрения передачи синтетических текстов выбранному провайдеру. Для OpenRouter обязателен `EMBEDDING_PROVIDER`. Одинаковые URL, провайдер, модель, размерность и версия индекса должны использоваться при импорте и поиске.
3. Из каталога `ai` выполните команду с полным путём к данным:

```sh
uv run --locked python -m ai_service.rag.import_documents knowledge/documents.json
```

4. После успешного импорта в отдельной базе ожидаются 45 строк `documents`, 45 строк `document_chunks` и 87 строк `document_access` (42 общие статьи × 2 роли и 3 статьи × 1 роль). Вектора заполняются активным профилем. Проверьте `/readyz` и вопросы из eval.

Сам файл не создаёт пользователей, диалоги, задачи, страховые полисы или статусы шагов. Даже наличие инструкции `dev-environment` не означает создание одноимённого шага в onboarding; его создаёт владелец onboarding. Импорт знаний не исправляет межсервисные контракты.

## Пример запроса к AI

Для деморежима с настроенным RAG и токеном сервиса:

```json
{
  "conversation_id": "demo-001",
  "actor": {"user_id": "42", "team": "101", "role": "intern"},
  "message": "Как забронировать переговорную на восемь человек?"
}
```

Отправить на `POST /api/v1/chat` с `Authorization: Bearer <AI_SERVICE_TOKEN>`. Ожидается ответ про «Неву», третий этаж, поле «Ресурс», подтверждение «Принято», лимит 2 часа и горизонт 30 дней, со ссылкой `[source:synth-book-meeting-room]`. Это эталон, а не результат выполненного запроса к модели.

## Проверка RAG

`eval_cases.json` — входные сценарии и ручные эталоны, а не исполняемый тест-раннер. В каждом есть `actor`, вопрос, ожидаемые/запрещённые ID источников и эталон поведения. Для двух вариантов вопроса к одной статье эталон объединяет её основные факты: отвечать нужно на запрошенную часть, без обязательного перечисления всего эталона.

90 `answerable`: проверить попадание нужного источника в доступный контекст и `sources`, факты в ответе и корректные ссылки. 6 `insufficient_knowledge`: не выдумывать личный оклад, пароль Wi-Fi, VPN-сервер, реальный адрес офиса, семейный тариф ДМС или production-секреты. 3 `restricted_source`: с ролью `intern` закрытые статьи не должны попадать в выдачу, контекст и ответ; допустима общая информация из открытых статей. У этих сценариев не задан обязательный HTTP-код отказа.

При проверке интеграционного режима берите существующего пользователя: сервис сам получает роль и команду из `user`. Подставление `mentor` в клиентский JSON прав в интеграции не даёт.

Проверены схема JSON, уникальность ID, ограничения импортера, права, иерархия, ссылки эталонов на документы и соответствие читаемой версии данным. Живой поиск с эмбеддингами и качество ответов LLM нужно оценить после загрузки в тестовую БД; здесь они не измерялись.
